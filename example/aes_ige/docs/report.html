AES-IGE: specification, algebra, and implementation

A byte-oriented AES-128/192/256 implementation extracted from CJR terms, with an explicit two-block IGE state and checked algebraic properties of a concrete AES model.

Exact verification coverage

The specification algebra is machine checked, including both inverse compositions and stateful chunk laws. The concrete byte and transformation kernels have Iris contracts. Full Iris refinement of key expansion, complete AES block routines, and the IGE loops remains outstanding. The runtime suites exercise those routines, but tests do not discharge those proof obligations. Implementation-level round-trip and chunk-composition contracts remain outstanding as a consequence.

Kernel/assumption audit: passed. Runtime tests: passed, 15 passed cases. Benchmark observations: 882.

Specification and conventions

A byte is an integer in 0..255. A block consists of four columns with four coordinates each; flattening uses the column-major layout from FIPS 197. Key expansion produces 176, 208, or 240 bytes for 10, 12, or 14 rounds. The final round omits MixColumns.

The S-box is defined independently through inversion in GF(2⁸), reduction polynomial 0x11b, and the affine transformation. A finite certificate verifies the executable lookup tables. Inverse MixColumns uses three forward applications, with a proof that this equals the standard inverse coefficient matrix.

IGE uses Cᵢ = AESₖ(Pᵢ XOR Cᵢ₋₁) XOR Pᵢ₋₁ and Pᵢ = AESₖ⁻¹(Cᵢ XOR Pᵢ₋₁) XOR Cᵢ₋₁. The mutable IV is C₀ || P₀ and ends as Cₙ || Pₙ, matching OpenSSL. Pure operations return (output, finalIV).

Algebraic validating properties

AES inverse compositions

Statement. decrypt(k, encrypt(k, b)) = b and encrypt(k, decrypt(k, b)) = b.

Assumptions. Byte-valued 16-byte blocks. The concrete schedule contains byte-valued round keys.

Proof. Each inverse round cancels AddRoundKey, MixColumns, ShiftRows, and SubBytes in reverse order. Induction on the round-key list cancels the entire cipher. The final round has its own inverse because it omits MixColumns.

Consequence. These laws are the basis for executable round-trip contracts once complete AES routine refinement is established.

Checked declarations: decrypt_encrypt; encrypt_decrypt

AES bijectivity

Statement. Encryption and decryption are injective and surjective on byte-valued blocks.

Assumptions. Fixed key and the same block domain.

Proof. Apply the inverse function to an equality for injectivity. For surjectivity, choose the inverse image and use the appropriate inverse composition.

Consequence. Each valid output block has exactly one valid input for the fixed key.

Checked declarations: encrypt_injective; decrypt_injective; encrypt_surjective; decrypt_surjective

Transformation inverse laws

Statement. Both orders of SubBytes/InvSubBytes, ShiftRows/InvShiftRows, and MixColumns/InvMixColumns are identity; AddRoundKey twice with the same key is identity.

Assumptions. SubBytes requires byte-valued coordinates. Row permutation and XOR cancellation hold for arbitrary integer coordinates.

Proof. A kernel-checked finite certificate checks the S-box on all 256 inputs against the finite-field definition and both inverse compositions. Row permutations cancel by direct coordinate computation. The MixColumns matrix has fourth power identity, proved using xtime linearity and bitwise Boolean algebra; its third power equals the FIPS inverse matrix with coefficients 14,11,13,9.

Consequence. The proved transformation kernels can be composed into forward and inverse rounds without assuming an opaque AES primitive.

Checked declarations: sub_inverse; inverse_sub; shift_inverse; inverse_shift; mix_columns_inverse; inverse_mix_columns; inv_mix_fips; xor_cancel

Byte XOR algebra

Statement. Associativity, commutativity, zero identity, self-cancellation, cancellation, and byte-range closure.

Assumptions. The algebraic equalities hold for all integers; closure requires byte-valued operands.

Proof. Use Rocq bitwise integer laws and bit extensionality. Masking commutes with XOR, so the XOR of two eight-bit values remains eight-bit.

Consequence. The IGE step proofs cancel both chaining XORs while preserving the byte domain.

Checked declarations: bx_assoc; bx_comm; bx_zero; bx_self; bx_cancel; bx_byte

IGE inverse compositions and final IV

Statement. Decrypting encrypted blocks, or encrypting decrypted blocks, recovers the input; the final IVs of the paired operations agree.

Assumptions. Both directions start from the SAME original IV. Message blocks and both IV blocks are byte-valued.

Proof. Each IGE step cancels the outer XOR, applies the concrete AES inverse law, and cancels the inner XOR. Induction carries the identical ciphertext/plaintext IV pair to the next step. The theorem returns both recovered blocks and the original operation’s final IV.

Consequence. Inverse processing must restore the original IV; it then recovers the message and reaches the same final ciphertext/plaintext state.

Checked declarations: ige_decrypt_encrypt; ige_encrypt_decrypt

IGE bijectivity

Statement. For fixed key, initial IV, and block count, both output transformations are bijections.

Assumptions. Byte-valued messages and IV. Bijectivity concerns output messages, with the final IV determined by the operation.

Proof. Apply the opposite direction to equal outputs for injectivity. Choose the opposite transformation as the preimage for surjectivity; range and length theorems ensure membership in the same domain.

Consequence. A fixed initial IV gives a unique plaintext/ciphertext correspondence at every supported block count.

Checked declarations: ige_encrypt_injective; ige_decrypt_injective; ige_encrypt_surjective; ige_decrypt_surjective

Length, range, and empty identity

Statement. AES produces 16-byte blocks; IGE preserves block count and byte range. Empty messages return an empty output and the unchanged IV.

Assumptions. Range preservation requires byte-valued message and IV inputs.

Proof. The fixed block record contains sixteen coordinates. Induction on the message establishes length and range preservation. Empty identity is the defining base case of both IGE functions.

Consequence. The specification fixes output capacity to input capacity and defines empty processing as an unchanged state.

Checked declarations: ige_encrypt_length; ige_decrypt_length; ige_encrypt_range; ige_decrypt_range; ige_encrypt_empty; ige_decrypt_empty

Chunk composition

Statement. Processing xs ++ ys equals processing xs and then ys using the returned IV, including equality of the final IV.

Assumptions. Chunks contain whole AES blocks. The pure theorem itself needs no byte-range premise.

Proof. Induction on the first chunk unfolds one step on each side and applies the induction hypothesis to the updated IV. Both output concatenation and final state follow.

Consequence. Clients can continue block-aligned chunks by retaining the mutated IV, with the same output and final state as a single call.

Checked declarations: ige_encrypt_chunks; ige_decrypt_chunks

Executable buffers and proof structure

All buffers contain Int64 words representing bytes. Input/output must be disjoint; the IV, schedule, and 64-word workspace must also be disjoint. Source and schedule are preserved. Capacity, ownership, and byte-range conditions are caller obligations. Invalid round counts and invalid message lengths return false before writes; invalid key lengths return zero before schedule writes.

Byte-kernel Iris proofs refine the grouped S-box lookup and arithmetic xtime to their pure definitions. Transformation contracts own sixteen source words and sixteen destination words, frame unrelated memory, preserve the source, and establish the transformed destination. The full scheduling and loop refinements are the remaining bridge between those kernels and the pure AES/IGE model.

CJR gains integer XOR and AND with Z.lxor/Z.land semantics, dedicated WP rules, extraction operators ^ and &, and renderer entries. Boolean conjunction remains a separate operation. Shift and multiplication primitives are unnecessary. Doubling is bounded by 510. The loop uses i ≤ len−16, with an arithmetic theorem establishing safe increment bounds under the Int64 message-length bound.

Performance

The extracted Cangjie implementation is compared with OpenSSL’s native C AES-IGE API on the same machine. Both use three processes, seven samples per workload, two warm-up calls, and adaptive batching to 20 ms or 16,777,216 repetitions. Throughput uses pre-expanded keys, includes IV reset and an output checksum, and is reported per logical byte. Key-expansion timings include a schedule checksum and are reported per forward expansion; OpenSSL inverse schedule setup is excluded from decryption timings and is not separately measured. Every output byte and final IV agrees across all throughput workloads before timing: differential validation. OpenSSL uses packed bytes, CJR uses Int64 words, and their algorithms and toolchains differ. Default OpenSSL dispatch is used; hardware instruction use has not been separately established. This compares practical implementations and does not isolate language overhead. Native compiler and library provenance records build flags, version, digest, and capabilities. Comparison charts and all measurements show medians and IQR. Jobs run sequentially, so small timing differences should not be overinterpreted.

Trust and limits

No admissions or additional cipher-correctness axioms are used. The Rocq kernel checks the algebraic proofs; Iris contracts depend on the existing CJR semantics. The printer and Cangjie toolchain remain part of the correspondence boundary. Full executable refinement is explicitly incomplete. Branch-based S-box lookup is not constant-time. Authentication, padding, cryptographic-security proofs, and side-channel proofs are outside scope.
