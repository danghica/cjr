A memory-only offline TOTP authenticator with a CJR core, a Cangjie interactive CLI, and a macOS SwiftUI app calling the same extracted core through FFI. The implementation follows the plan and the ports and adapters dependency boundary.

  • core/: CJR implementation, specifications, Iris proofs, extraction and native tests.
  • cli/: command adapter, interactive terminal, clock and URI adapter.
  • ui/: SwiftUI views, application adapter, C ABI and Cangjie runtime adapter.
  • scripts/: frontend build composition; test/: shared enrollment fixtures.
  • docs/: API reference, proof evidence and Rocq-readable pages.

The HTML API reference documents all extracted functions, including their arguments, results, side effects, and current proof links. Readable Rocq documentation, including the declaration dependency graph, is in the generated index. Regenerate it with make -C example/authenticator readable from the repository root. Set EXPLANATIONS=offline to use only cached explanations; the default generates missing explanations through the configured Codex CLI.

  • SwiftUI macOS app — setup, enrollment and account controls, FFI ownership and C4 hexagonal architecture.

Status and proof coverage

The core is implemented as CJR terms and extracted to compilable Cangjie. Runtime tests exercise SHA-1, HMAC-SHA-1, HOTP, TOTP, Base32, and account sessions. The proof-status ledger records the completed proof-first gate: all 69 core modules pass coqchk, all 580 core declarations have closed assumptions, and all 20 extracted functions have mapped implementation contracts. The repository-wide make verify passes with 936/936 declarations closed. All nine native runtime test groups and both frontend integration suites pass.

No theorem claims cryptographic security, constant-time execution, or guaranteed secret erasure. Compilation/runtime, allocation success, and platform adapters remain outside CJR's proof boundary. Inputs to extracted functions must respect the buffer ownership and capacity requirements below.

Build and check

With the repository's Rocq and Cangjie toolchains available:

make -C example/authenticator build
make -C example/authenticator extract
make -C example/authenticator test
make -C example/authenticator proofs
make verify

The proofs target checks all authenticator proof objects with coqchk and audits every declared lemma, theorem, and example. Its source-hashed report is example/authenticator/build/proof-report.json; core/contracts.json maps every export to its implementation theorem. This is functional refinement of the specified program, not a cryptographic security certification.

The extraction script evaluates print_prog authenticator_program in Rocq; it does not hand-write or patch the generated Cangjie. make extract and make test at the repository root include this core. Runtime artifacts are written to example/authenticator/build/: compiler log, execution log, and JSON report.

The test runner generates deterministic independent oracles using Python hashlib, hmac, and base64, plus explicit RFC 4226/6238 fixtures. Coverage includes padding boundaries, keys crossing the HMAC block size, six/eight digits, period boundaries, post-2038 and maximum signed timestamps, malformed Base32, capacity, session isolation, identifier exhaustion, and whole-session snapshots on failure. Test inputs contain synthetic secrets only.

Run the interfaces

Frontend builds require the passed, current core proof and runtime reports above. Use the pinned Cangjie 1.0.5 toolchain. SwiftUI additionally requires a complete Xcode installation; DEVELOPER_DIR overrides /Applications/Xcode.app/Contents/Developer. The bridge uses that Cangjie version's runtime header Cangjie.h; set CANGJIE_RUNTIME_INCLUDE if it is outside the sibling runtime source checkout. The current build targets Apple Silicon and has been tested on macOS 26.

make -C example/authenticator frontend-test
make -C example/authenticator docs-check
make -C example/authenticator run-cli
make -C example/authenticator run-ui

The CLI supports help, help <command>, add, uri, list, code <id> [unix-seconds], rename <id>, remove <id>, and quit. Enrollment prompts read secrets from standard input, rather than command-line arguments. For example, enter add, answer the prompts, then code 1 59. EOF and quit destroy the session. A second invocation starts empty.

The SwiftUI app supports manual or URI enrollment, account list, zero-padded codes, live countdown, copying a code, rename and confirmed removal. Quit the app to discard the session. UI mutations and timer refreshes run on the main actor, and the bridge serializes core access. Each interface has an independent session; accounts do not transfer between processes. Duplicate labels are allowed.

All authenticator build artifacts are under example/authenticator/build/ (build/ inside the authenticator directory). Frontend binaries are under example/authenticator/build/frontend/, including Authenticator.app and the CLI authenticator. These are development artifacts linked to the local Cangjie SDK and build paths, not a relocatable distribution. Do not move the bundle independently of its libraries. Packaging for distribution and secure persistence are outside this prototype's scope.

Both enrollment adapters accept otpauth://totp with secret, optional issuer, algorithm=SHA1, digits=6|8, and period=1..2147483647. Defaults are six digits and 30 seconds. They reject unknown/duplicate parameters, HOTP URIs, issuer-prefix mismatches, invalid UTF-8/percent escapes and control characters. Plus signs are literal, so use percent encoding for spaces. The core performs canonical Base32 and parameter validation; neither frontend calculates OTPs.

Integration tests use five accepted and eighteen rejected shared URI fixtures, RFC codes including leading zeroes, boundary times, independent sessions, capacity rejection, metadata changes, removal, EOF/close, and ABI output-capacity checks. Test secrets are public synthetic fixtures. The app compiles and stays running after desktop launch; visual interaction has not been validated because the desktop automation tool times out.

Core interface and buffer contract

All buffers are CPointer<Int64> with one logical byte per word, not packed bytes. Byte values must lie in 0..255. Callers own sufficiently large live buffers. The session must be a live authNew result and must not be changed outside these operations. Calls on the same session must be serialized. Never use a destroyed pointer or supply an input/output buffer overlapping session storage. Outputs must have their documented capacity and not overlap inputs. Read-only input buffers may overlap each other.

Cryptographic operations:

  • authSha1(src, n, dst): 0..2048 input bytes, 20 output words; returns Bool.
  • authHmac(key, keyLen, msg, msgLen, dst): 1..128 key bytes, 0..1024 message bytes, 20 output words; returns Bool.
  • authHotp(key, keyLen, counter, digits): nonnegative signed Int64 counter, six or eight digits; returns a numeric code or -1 for invalid arguments.
  • authTotp(key, keyLen, timestamp, period, digits): nonnegative Unix seconds, period 1..2147483647; returns a numeric code or -1. The epoch is zero.
  • authRemaining(timestamp, period): returns 1..period, including a full period at the boundary, or -1 for invalid arguments.
  • authBase32(src, n, dst): 2..208 ASCII input words, 128 output words; returns the decoded length or -1. Accepts upper/lowercase and optional canonical = padding, rejects whitespace and nonzero unused bits, and requires 1..128 decoded bytes. It validates in scratch storage before writing the result.

Numeric codes retain their configured digit count in account metadata; both adapters zero-pad when displaying them. No algorithm selector is exposed: this version supports SHA-1 only. HMAC/HOTP/TOTP do not call external crypto.

Session operations:

  • authNew() / authDestroy(session): allocate/dispose an independent session. Destruction overwrites session words before freeing in the source program; no platform-level erasure guarantee is made.
  • `authAdd(session, label, labelLen, issuer, issuerLen, secret, secretLen, digits, period)`: Base32 secret input; returns a positive identifier, -1 for invalid input, -2 for capacity, or -3 for exhausted identifiers.
  • authList(session, dst): capacity 16 words; writes live identifiers and returns their count. Ordering is unspecified.
  • authRead(session, id, dst): capacity 260 words; returns Bool. Writes [digits, period, labelLen, issuerLen], label at offset 4, issuer at offset 132. Only the indicated string lengths are meaningful; it does not expose secret length or secret material.
  • authRename(session, id, label, labelLen, issuer, issuerLen): updates display metadata, returning Bool.
  • authRemove(session, id): overwrites the slot, returning whether it existed.
  • authCode(session, id, timestamp): returns a code or -1. Use authRead for digits/period and authRemaining for the countdown.

Sessions hold at most 16 accounts. Labels are 1..128 opaque bytes and issuers 0..128 opaque bytes; encoding and URI syntax are adapter concerns. Duplicate labels are allowed. Identifiers are monotonic and are never reused during a session. Failure preservation is proved and covered by runtime tests; the concrete removal proof establishes the exact 390-word slot wipe. This models source-level writes, not guaranteed physical erasure.

The 6242-word session layout is internal: next identifier and live count in two header words, followed by 16 slots of 390 words. Each slot contains identifier, digits, period, label length, issuer length, secret length, then three 128-word regions for label, issuer, and decoded secret. External consumers must use the operations rather than depending on these offsets.
